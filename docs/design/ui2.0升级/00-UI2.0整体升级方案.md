# Ling UI 2.0 整体升级方案

Status: active UI2 product and architecture contract
Owner: UI platform maintainers
Last verified: 2026-08-03

## Objective

UI 2.0 将 Ling 从“页面各自实现控件和样式”升级为一套 Web 与 Electron Desktop
共用的产品界面系统。目标不是换皮，而是让任何页面都使用一致的视觉层级、交互、
状态反馈和可访问性规则。

当前合同覆盖可达 Web 主界面、Settings、Desktop 主窗口、原生启动恢复、Computer Use
current-session control 和独立 PiP renderer。历史视图数量、CSS 行数、selector 数量和逐文件迁移
统计由 Git 历史保留，不作为长期合同。

## Product Principles

- **安静**：不使用营销式 Hero、卡片墙、装饰渐变和无任务价值的大标题。
- **紧凑**：控件、列表和 Inspector 面向持续工作，不使用过大留白。
- **可扫描**：对象、状态、主行动和需处理事项进入稳定网格。
- **语义优先**：先说发生了什么、用户能做什么；技术原因进入详情。
- **诊断折叠**：raw id、path、hash、metadata、transport、adapter、checksum 默认隐藏。
- **真实反馈**：loading、disabled、失败、排队和审批必须反映真实状态。
- **双表面**：Web 清晰克制；Desktop 可增加有限材质，但共享组件和语义不分叉。
- **多窗口一致**：Desktop main window、PiP 和未来 utility window 使用同一 Theme Pack、
  图标、状态、反馈和键盘合同，不建立第二套视觉实现。
- **连续交互**：点击、展开、切换和拖动解释状态变化，可反向、可打断、可降级。
- **独立主题包**：Light/Dark 是平级 Theme Pack，System 只负责解析选择。
- **Token 换肤**：主题改变语义颜色和 surface，不改变布局、控件尺寸和业务行为。
- **受控表现配方**：主题可选择 Ling 内置 Presentation Profile，实现全窗口背景、磨砂和
  固定装饰槽位，但不能上传 CSS、DOM 或改变业务布局。
- **可生成主题**：快速模式本地编译，生成模式使用生图能力，高级模式使用结构化 Planner
  与生图能力；所有输出由 Theme Compiler 验证。

## Visual Baseline

- 以黑白中性色为主，只为 success、warning、danger、info 使用语义色。
- 页面区块默认不使用卡片边框；重复对象和真正的工具框架才可使用容器。
- 卡片、Dialog、Drawer 和 Popover 圆角不超过 `8px`。
- 主行动每个任务区域最多一个；低频行动进入 Menu、Details 或 Inspector。
- 熟悉操作优先 icon-only，必须提供 Tooltip、title 或可访问名称。
- 普通 UI 图标统一使用 Lucide SVG；品牌、语言和内容图片按 iconography 文档处理。
- 当前 Ling Logo、favicon 不替换、不重绘、不改色、不改比例。
- 可增长列表必须有滚动边界，长标题截断但不得挤压操作。
- 灰色说明只能补充后果、限制或修复路径，不能重复标题和字段。
- 字号不随 viewport 连续缩放，letter-spacing 固定为 `0`。
- 动效使用 `120/180/240ms` 统一 tokens，不使用摇晃、弹跳或装饰性循环动画。
- 主题包只能替换 semantic tokens、Desktop surface 和受限本地背景资源。
- Presentation Profile 只由共享包实现，Theme Pack 只能选择已批准 Profile 和强度。
- `LingStackLogo`、favicon、Lucide 映射、字号、间距和控件 geometry 不随主题变化。

## Shared Architecture

```text
apps/web features ──> apps/web/src/shared/ui ──┐
                                               ├─> @ling-stack/ui-react
Electron renderer ─────────────────────────────┘            │
                                                             └─> Radix + Ling CSS

Desktop utility renderer ───────────────────────> @ling-stack/ui-react compact-window primitives
```

- `@ling-stack/ui-react` 只拥有展示、交互和样式，不拥有 API、路由、i18n 或业务状态。
- `apps/web/src/shared/ui` 只处理翻译、Provider 和 Web 默认参数，不复制组件 JSX。
- `conversation-ui-react` 可以依赖 `ui-react`；`ui-react` 不得依赖会话包。
- Radix 只能出现在共享包内部，功能页面不得直接拼装 Radix primitives。
- Desktop 复用组件、tokens 和状态语义，只在窗口 chrome 和 surface tokens 上变化。
- `@ling-stack/ui-react` 拥有 Theme Pack schema、内置主题、registry 和 token 映射；
  Presentation Profile、Theme Compiler 和生成合同；Web/Desktop adapter 拥有持久化、
  本地导入和模型/媒体任务连接。
- CSS 使用明确 cascade layers；遗留兼容和后续删除规则以
  [迁移与兼容合同](migration/README.md)为准。
- Overlay、Tabs、Disclosure、Sidebar、Dock 和 Terminal 使用统一可打断状态转场。

## Standard Page Grammar

```text
PageShell
  PageHeader
    Object identity
    Primary action
    Secondary actions
  PageToolbar
    Search / filter / view controls
  PageContent
    List / workspace / canvas
  Optional Inspector
  Overlay layer
```

Settings 使用独立 Settings shell。会话使用固定 Header、Feed、Composer、Bottom
Panel、Right Dock。业务页面不能创造新的页面语法，除非在模块文档中说明原因。

Desktop utility window 使用 CompactDesktopWindow 语法：captured/content layer、compact header、
status overlay 和 action menu。它不是 PageShell，也不能复制 AppShell。

## State Model

每个控件和页面必须设计：

- default、hover、focus-visible、active、selected；
- disabled 并说明原因；
- loading、queued、saving、refreshing；
- empty、no-result、stale；
- success、warning、error、blocked；
- destructive confirmation；
- long content、overflow、scroll；
- `ling-light`、`ling-dark`、System resolution、imported theme、Desktop surface；
- keyboard、screen reader、reduced motion。
- Desktop native prompt、window resize/drag、DPI/Retina、forced colors/reduced transparency。

## Scope Boundary

UI 2.0 不修改 daemon API、contracts、数据库、路由、权限和状态机，不调整主导航 IA。
如果迁移发现现有能力无法支撑产品状态，必须记录 blocker 并另开业务设计，不能用假状态
或前端本地状态绕过。

## Current Delivery Boundary

可达 Web UI2 主迁移已经关闭。Work Board、Startup/Diagnostics、Workspace Tools 嵌入态和
Desktop Theme 原生发布仍由 [实施状态索引](../implementation-status.md)管理。packaged Desktop、
Computer Use PiP、签名和真实平台验收由发布清单管理。

任何阶段都不能以“页面看起来差不多”作为完成标准；完成必须满足
[UI2 验收规范](03-UI2.0验收总规范.md)，运行证据进入 CI 或 Release artifacts。
