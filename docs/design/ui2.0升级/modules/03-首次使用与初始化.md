# 首次使用与初始化

## Goal

首次使用只引导用户完成可运行 workspace、provider/model 和初始化检查，不解释内部模块。
流程必须告诉用户当前步骤、失败位置和修复行动。

## Function Points

- `FIRST-WORKSPACE-001`：选择/确认 workspace。
- `FIRST-PROVIDER-001`：选择 provider、模型和 API Key。
- `FIRST-CHECK-001`：配置检查与失败修复。
- `FIRST-PROGRESS-001`：步骤进度、返回和重试。
- `FIRST-COMPLETE-001`：完成并进入可工作的页面。

## Structure

使用单一 Dialog/全页流程：步骤标题、必要字段、当前检查摘要、单 primary CTA。Advanced 和
raw error 默认折叠。步骤切换不改变容器尺寸，失败停留在当前步骤。

## States

workspace missing/invalid、provider loading、model empty、API key missing、check running、
check failed、partial ready、complete。Ling Agent 可用后才能完成；非阻塞可选项不阻止。

## Components

Dialog、Field、Select、Button、StatusIndicator、InlineFeedback、Progress/Skeleton。禁止使用
多个彩色步骤卡片。

## Approved Product Entry

截至 2026-07-20，仓库中的 `features/workspace/FirstRunFlow.tsx` 只从 workspace barrel 导出，没有生产
import 或可达入口；当前 13 个 `ViewId` 也没有 onboarding/first-run view，`AppShell` 没有首次启动 gate，
E2E 没有真实 workspace/provider/check/complete 流程。它是旧的“provider -> channel -> task -> run”面板
实现，不能作为当前首次启动体验已经存在的证据，也不应先做视觉迁移。CLI 注入默认 cwd 只提供 workspace
默认值，不等于完成标记、跳过语义或恢复协议。

2026-07-30 产品决定选择 A：实现柔性首次引导。首次配置未就绪时自动出现，但用户可随时跳过并继续使用，
不得锁死产品。新入口使用 AppShell overlay Dialog，不增加 `ViewId`，也不复活旧 channel/task/run 流程。

## Trigger And Readiness

控制器只在以下数据均已稳定后判断是否自动打开：

1. daemon 健康状态已经确定；
2. workspace cwd 初始化完成；
3. provider 列表完成首轮加载；
4. 当前版本没有 `skipped` 或 `completed` 记录。

当 workspace 为空、daemon 不可用，或没有可运行的 chat provider 时，均视为“需要引导”。已存在可运行
workspace 和 chat provider 时保持静默并写入完成记录，避免已配置用户看到引导。短暂 loading、后台刷新和
网络抖动不得触发 Dialog 闪现。

## Persistence Contract

前端拥有版本化 UX 偏好，存储键为 `ling-first-run:v1`，不写 daemon 或 SQLite：

```ts
interface FirstRunPreferenceV1 {
  version: 1;
  status: "skipped" | "completed";
  workspaceIdentity?: string;
  updatedAt: string;
}
```

- `workspaceIdentity` 使用 cwd 的标准化字符串，仅用于判断同一安装的引导状态，不包含 secret。
- 跳过和完成跨刷新、Web 重开和 Desktop renderer 重启保留。
- v1 记录对当前产品版本全局生效；切换 workspace 不自动重复打扰。未来若引导合同有破坏性变化，以 v2
  新键重新评估，不覆盖历史 v1 记录。
- localStorage 不可用时允许本次会话继续或跳过，但必须保持非阻塞；不可因此锁死应用。
- Settings/帮助中的手动“重新打开引导”入口不在本切片范围，后续可调用同一控制器而不修改存储合同。

## Flow And Recovery

新流程为三个固定步骤，每步只有一个主动作：

1. Workspace：显示当前工作目录是否可用；缺失时提供“继续使用当前目录/稍后设置”，不加入路径输入墙。
2. Model：显示是否存在可运行 chat provider；缺失或检查失败时主动作打开 Settings > 模型工作台。
3. Check：汇总 workspace 与模型状态；全部就绪时完成并回到原页面，部分就绪时可重试或继续跳过。

关闭按钮、Esc 和“稍后再说”进入同一个 skip handler。打开模型工作台属于修复导航：先关闭 Dialog、记录
本次已跳过，导航到既有 Model Workbench owner；用户完成模型配置后不由引导复制配置表单。失败保留在当前
步骤并显示产品化原因，不暴露 raw provider ID、路径栈或 daemon 错误。
